SQL 优化实践

慢 SQL 是性能问题的头号来源

📅 2021-07-16⏱ 2 分钟阅读🗄️ 数据库与中间件

慢 SQL 是性能问题的头号来源。先找到它，再优化它。

开启慢查询日志

SHOW VARIABLES LIKE 'slow_query_log';

SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过 1 秒记录
mysqldumpslow -s t /var/lib/mysql/*-slow.log   # 按耗时排序

常见优化手段

1. 避免 SELECT *

-- 不好：回表 + 传输大量无用列
SELECT * FROM order_table WHERE status = 1;

-- 好：只取需要的列，尽量覆盖索引
SELECT id, order_no FROM order_table WHERE status = 1;

2. 分页优化

深分页 LIMIT 100000, 20 会扫描前 10 万行，用延迟关联：

-- 不好
SELECT * FROM order_table ORDER BY id LIMIT 100000, 20;

-- 好：先取主键再关联
SELECT t.* FROM order_table t
JOIN (SELECT id FROM order_table ORDER BY id LIMIT 100000, 20) tmp
ON t.id = tmp.id;

或基于游标：

SELECT * FROM order_table WHERE id > 100000 ORDER BY id LIMIT 20;

3. JOIN 与子查询

-- 避免在 WHERE 里写子查询做逐行判断
-- 改 JOIN
SELECT u.* FROM user u
JOIN user_role ur ON u.id = ur.user_id
WHERE ur.role_id = 1;

关联字段要有索引，小表驱动大表。

4. 合理使用索引

EXPLAIN SELECT ...;
-- 关注 type、key、rows、Extra

常见陷阱

写法 问题
WHERE name != 'x' 一般不走索引
WHERE status IN (1,2,3) 数据量大时慎用
OR 连接非索引列 索引失效
函数包住索引列 索引失效
大量 count(*) 大表 考虑缓存或汇总表

总结

  • 慢日志定位问题 SQL
  • EXPLAIN 验证执行计划
  • 分页用游标/延迟关联，查询只取必要列
